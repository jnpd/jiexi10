# 01｜逐步开发实施手册（按这个顺序动手）

> 面向开发人员的操作手册：每步都规定**做什么、怎么做、产物、怎么验证**。只提供实现方案；本仓库目前没有已完成的后端代码。单机 MVP 可先使用 Python/FastAPI + MySQL/SQLite，成熟后换 RabbitMQ Worker。

## 第0步：确定工作范围与目录

1. 定义参数模板为任务级输入，不在程序中写死31个字段；源客户文件逐一建立 `documentId`，RFQ/订单/澄清独立作为附件并记录绑定关系。
2. MVP 先支持**有文字层的 PDF 和 XLSX**；扫描 PDF 进入“需视觉解析/OCR备选”路径，不要当作空白文档。
3. 实现导出模式 `STANDARD_SERIES`（展开技术规格的系列）、`EXPLICIT_SPEC`（限定 Scope/专属表所明确的产品）、`ORDER_CONFIRMED`（必须存在正式订单证据）。这三种是**选择/审查的口径**，单个产品可以同时满足多个标签，不是三类互斥的产品。
4. 所有 JSON 输出需记录版本：`parserVersion`、`promptVersion`、`ruleVersion`、`templateHash`、`documentHash`。

建议后续落地目录：

```text
service/
  app/api/{tasks,documents,products,reviews,exports}.py
  app/core/{settings,security}.py
  app/models/{schema,entities}.py
  app/services/{template_reader,document_reader,ai_extractor}.py
  app/services/{series_resolver,scope_resolver,product_expander}.py
  app/services/{parameter_resolver,validator,excel_writer}.py
  app/workers/parse_pipeline.py
  tests/fixtures/{edm_11kv,edm_22kv}/
  tests/{test_product_expansion,test_param_rules,test_excel}.py
docs/  # 实施文档
```

## 第1步：创建解析任务和文档清单（程序）

**输入**：模板1份、客户文件N份、可选关联文件、项目/操作者和期望范围。

**怎么做**：
1. API 扫描文件扩展名与真实 MIME、限制大小/页数/压缩包炸弹、病毒检测；上传只存私有文件服务，原文件不可覆盖。
2. 对每个文件算 SHA-256，生成独立 `documentId`；相同文件可物理复用但逻辑上要保留本任务的引用。
3. 参数确认表取版本快照，上传后不应再被旧任务覆盖；另记导出策略、用户/租户权限。
4. 写 `parse_task`、`source_document`、`template_version`；初态 `UPLOADED`。
5. 异步执行时使用持久任务/消息队列，接口立即返回 `taskId`；不要在HTTP请求里同步跑大文档。

**输出**：`manifest.json`，列出 taskId、sourceDocumentIds、模板版本、范围模式及文件哈希。

**验收**：上传2个PDF+1模板，得到2个源客户文档ID；同名文件不覆盖；文件散列可复核，用户不能下载其他租户文件。

## 第2步：读取《参数确认表》（程序，不能交给 AI 自由发挥）

**输入**：模板 xlsx。

**怎么做**：
1. 使用表格工具查找包含“序号/分类/参数字段/单位”的表头，允许可配置列映射，不要固定“第3列是字段名”。
2. 按原表顺序抽取 `fieldCode, fieldName, category, unit, required, referenceValues, aliases, index`；缺失`fieldCode`时稳定生成 `F001` 等，但同一模板后续引用按版本+code。
3. 检查空行/合并单元格/重复字段；对同名不同单位字段必须报错或显式消歧。
4. 校验单位字段示例：“空载上限”单位 `%`、损耗 W 数值另行保存到 `noLoadLossW`，不能填入 %。
5. 生成版本化的 `template_fields.json`；下游处理字段时只遍历它，不允许 AI 加减 Sheet 字段。

**输出**：有序字段定义数组（本次示例31项，未来以新模板为准）。

**验收**：模板新增/删除某一字段后无需修改程序，所有产品 Sheet 参数行自动增减并保持原顺序。

## 第3步：逐份文件解析页面并构建证据索引（程序）

**输入**：一个源PDF/Excel及其文档ID（每个文档执行同一管道，严禁合并成一个原文语料）。

**怎么做**：
1. PDF 使用 PyMuPDF 抽取各页字符及布局坐标；表格可辅以 pdfplumber；保留页码从1开始的物理页序。
2. 记录每页 `pageText`、`textBlocks`、`tables`、`annotations`、`imageRefs`；表格记录行列、跨页和列头位置。
3. 把 PDF 中显式批注（包括中文修订）视作**独立证据来源**；与正文矛盾时标记冲突，未经人工批准不可覆盖。
4. XLSX 记录 sheet、单元格地址/表格坐标、值和单位；公式保存原式及可用计算值，不只读显示文本。
5. PDF 出现图片表格、文本层损坏或重要表格错行时，提交**指定页图像**给多模态模型或 OCR 校验，避免整个文件无差别 OCR。
6. 对章节标题建立索引：Scope、Requirements、Rated kVA、Electrical Ratings、Losses、Annex GTP、RFQ/PO；记录原文引用块的 stable `evidenceId`。

**输出**：`pages.json` 和可检索的 `evidence_blocks.json`。

**验收**：可根据一个 evidenceId 找到某文件的第12页§5.5.1原句，看到 9 个容量；能看到第24页附录说明。

## 第4步：AI 识别基础维度（不是猜全组合）

**输入**：当前文件的关键章节/表格证据；必要时同时提供页面截图。

**怎么做**：
1. 第一轮只问“**该文件明确出现哪些产品系列与具体四维组合**”，禁止抽取所有31项。
2. 要求模型逐条返回 `phase`（1P/3P）、`ratedHvKv`、`ratedLvLineKv`、`lvConfigurationRaw`、`capacitiesKva`、`evidenceIds`、`rawText`、`ambiguities`。
3. 同时标记数值角色：`11kV`是额定高压；`12kV Um`是设备最高电压；`400/230V`是线/相电压；`±5%`是分接范围；`25kA`是短路电流水平。
4. 不得仅凭标题决定全容量；正文的容量表、Scope、附录和订单互相验证。
5. 严格输出 JSON Schema；失败用限定次数重试并输出可观测错误，不得返回半截 JSON 当成功。

**输出**：`series_candidates.json`，每条都有明确来源证据，不需要此时生成 Excel。

**验收**：11kV EDM 示例识别出 3P/11kV/0.4kV、标准9个容量；22kV保持独立，绝不误把12/24kV的Um当作额定高压。

## 第5步：判断“产品属于哪一种范围”（AI 识别、程序管控）

**输入**：Scope/容量系列/Annex GTP/订单或RFQ的证据集合。

**怎么做**：
1. 为每项四维候选分别收集 `scopeClaims`：`STANDARD_SERIES`（被规范列举为可用系列）、`EXPLICIT_SPEC`（明确指向该规格的Scope/技术表）、`ORDER_CONFIRMED`（有订单或RFQ确认）。
2. 保存 `claimStatus=SUPPORTED/CONFLICT/UNVERIFIED`；不根据“文档标题11kV”暗示所有容量实际采购。
3. 当 Scope 写75kVA、章节列9个容量：**保留两种结果**，标记“全标准系列9条；明确范围1条；采购未确认”，让前台选择导出模式。
4. 同文档出现多个额定电压及容量但没有组合对应关系时，不交叉笛卡尔积；写到待澄清候选中。
5. 可设置默认导出模式为 `STANDARD_SERIES` 以兼容既有18 Sheet测试，但页面一定显示“全系列技术规格，并非采购清单”。

**输出**：`scope_claims.json`、`unresolved_links.json`。

**验收**：不再把§5.5.1中的9款直接认定成9个已订货型号。

## 第6步：生成、标准化、去重具体产品行（程序）

**输入**：SeriesCandidate + ScopeClaim。

**怎么做**：
1. `phase`统一为 `1P/3P`；`ratedHvKv`/ `ratedLvLineKv`/ `capacityKva`使用十进制 Decimal，按单位换算。
2. `400/230V`在确认是三相四线Y制时归一为 `ratedLvLineKv=0.4`，保留 `rawLowVoltage=400/230V`；不是同时生成0.4和0.23两个产品。
3. 按证据支持的`(phase,hv,lv,capacity)`明确组合展开，不生成“看起来可能有的”组合。
4. 同一个源文件内按四维键去重，并合并**来源声明**；不同原文候选冲突则保留为待确认，禁止自动丢掉证据。
5. 跨文件计算汇总时默认按源文件分别计数。合并唯一规格数量需另设统计列、注明口径。
6. 生成 `productId` 的稳定内部ID（ULID/UUID或独立哈希），产品键不使用显示名或损耗值作为唯一标识。

**输出**：可直接在UI列出的 `ProductItem[]`，每条都有证据、适用范围、是否可导出。

**验收**：EDM标准模式下11kV恰好9行、22kV恰好9行；再次解析同一文档不随机重复。

## 第7步：AI 按模板抽取“参数规则”而非只给扁平值

**输入**：模板字段定义 + 当前文档索引 + 产品行列表。

**怎么做**：
1. 以模板 fieldCode 为索引，找 `rawValue`、`normalizedValue`、`unit`、`operator`、`semanticType`、`condition`、`evidenceIds`。
2. `semanticType` 区分 `REQUIREMENT_LIMIT`、`BIDDER_GUARANTEE`、`MEASURED`、`TEST_TOLERANCE`、`REFERENCE_ONLY`，绝不混写。
3. 适用条件用机器规则对象表达，例如 `capacityKva <=315`；`75kVA`有损耗200W/910W；明确全系列 `frequency=50Hz`。
4. 源表`Vendor to state`只说明“供应商待提供”，不应输出具体数值。
5. **同时保存不属于模板字段的可用于命名/分析的数值**，如损耗的W值（模板上限字段为%时不得覆盖）。
6. 以段落/表格批次分批提交，避免丢失后面的附录；跨页或多段证据带上关联 ID。

**输出**：`parameter_rule_candidates.json`，尚未强制写入某产品。

**验收**：75kVA的200W不会被错误归入空载上限(%)；阻抗`-5/+10%`被识别为允差而非标称阻抗。

## 第8步：按规则填充每个产品全部字段（程序）

**输入**：ProductItem[] + ParameterRule[] + TemplateFields[]。

**怎么做**：
1. 初始化每个 ProductItem 的全部模板字段为 `NOT_FOUND`，字段名/单位固定从模板复制。
2. 遍历规则，运行`rule.condition.matches(product)`；**只有 condition 匹配才允许赋值**。
3. 具体容量/额定电压专属优先于范围通用；但同优先级来源冲突、正式澄清与正文冲突均保留两候选并标记`CONFLICT`，不能静默覆盖。
4. 未出现填写`未提供`；`Vendor to state`填`待供应商提供`；真正不适用填`不适用`，三者区分。
5. 每个字段决议保存`ruleId/evidenceIds/decisionReason`，方便审核后解释“为什么75有200W而100没有”。

**输出**：`product_field_decisions.json`，字段数=产品数×模板字段数。

**验收**：标准系列 18 个产品 × 31 个字段 = 558 条模板字段决议；这不是非空值数量。

## 第9步：自动复核与异常列表（程序）

**输入**：结构化决议和原文证据。

**怎么做**：
1. **结构检查**：缺维度、重复键、每产品字段数量不符、缺页码/来源。
2. **单位检查**：W不可写入%字段；K温升与℃温度区分；50Hz不得误识成容量。
3. **语义检查**：比较符`≤`、偏差`-5/+10%`、规范上限与厂家保证值均保留。
4. **容量范围检查**：条件不匹配禁止继承；缺少明确组合的多电压表格进入人工审查。
5. **跨文档检查**：一个字段引用其他documentId的证据，直接阻断（除非明确是绑定的采购附件且记录来源关系）。
6. **原文验证**：匹配值和页码中的引用字符串/表格单元格；无法验证标记 `UNVERIFIED_EVIDENCE` 并要求复核，不把模型自述当客观证据。

**输出**：`validation_issues.json`，每项具严重程度、产品、字段和修正建议。

**验收**：针对“500kVA空载=200W”“22kV产品使用11kV PDF页码”造负例，必须提示或阻断。

## 第10步：人工审核（UI 后做；MVP可使用JSON修正文件）

**输入**：产品行列表 + 字段及来源 + 验证异常。

**怎么做**：
1. UI左侧文件与产品树，中央参数表，右侧PDF定位/放大 + 原文对照。
2. 审查者可选择“包含标准系列产品/只导出明确规格/按订单确认”，并填写原因；不可把原文删改掉。
3. 编辑字段时保留 `before/after/user/time/reason`；修改后重新校验本产品/受影响的分档产品。
4. 审查强制阻断项：无证据的四维主键、跨文件来源、冲突未解决、订单范围错误。
5. 确认后冻结一个不可变 `confirmedSnapshotId`；后续修改生成新版本，不直接改旧确认数据。

**输出**：确认产品集合、字段决议、审计日志、锁定快照。

**验收**：修改75kVA阻抗的审核值后，重导Excel反映修订；原文值和人工修改前值仍可查询。

## 第11步：产品命名、Excel导出及校验（程序）

**输入**：一个源文档的确认快照 + 该次模板。

**怎么做**：
1. 命名严格按`材质-容量-高电压-低电压-空载-负载-阻抗-频率`；未知字段使用`材质待定`、`空载待定`等，不编造。
2. 一份源文档一个工作簿；**工作簿中仅有具体产品Sheet**，不加汇总/封面 Sheet。
3. 单系列可以按`50kVA/75kVA`命名 Sheet；多个电压/相数则加前缀（31字符限制、冲突后缀处理）。完整产品名置于表头而非依靠Sheet标签。
4. 每张Sheet写表头：客户、来源、产品名、主键属性/语义说明；正文遍历模板字段数组写`序号/分类/字段/单位/值/状态/证据`。
5. 输出额外 `全任务汇总.md` 与可选 JSON；统计表不能占用该Excel的产品Sheet名额。
6. 导出后**重新读入生成文件**验证：Sheet数=本文件选中产品数，行数、字段顺序、字段单位、产品名和内容匹配；失败即任务失败、不能给下载链接。

**输出**：`document-{id}-产品参数.xlsx`、`summary.md`、校验报告。

**验收**：11kV9张+22kV9张，分别完整31字段；75kVA名称含200W/910W，其他容量损耗待定。

## 第12步：异步状态、回调和正式数据对接（MVP之后）

**输入**：确认快照。

**怎么做**：
1. 任务状态 `UPLOADED→PREPROCESSING→EXTRACTING_SERIES→EXPANDING_PRODUCTS→EXTRACTING_PARAMS→VALIDATING→REVIEW_REQUIRED→CONFIRMED→EXPORTING→COMPLETED`，异常 `FAILED`可按环节重跑；审查未通过禁止确认。
2. 每步写耗时、模型token/调用、规则版本和错误类型；模型超时有限重试+退避，重试不重复产品。
3. A 子系统对主程序发送签名Webhook（只带 taskId/snapshotId/事件类型），主程序用服务端token再拉取确认数据。
4. 主程序按 `snapshotId + documentProductKey` 幂等落 ProductItem；`PARAM-V1`仅由主程序批准的业务流程生成。
5. 安全要求：租户隔离、上传白名单、恶意提示词不作为指令、模型API密钥服务端持有、过期文件删除和日志脱敏。

**验收**：Webhook重复3次不会新建3份产品；暂时无法回调可重试，确认快照版本一致。

## 最先做的5个可运行单元测试

1. 11kV规范9个容量→9行，`400/230V`不额外生成0.23kV行。
2. 11kV+22kV分别独立→`9 + 9`，不串用任何证据。
3. 当 `capacity=75` 时得到损耗 200W/910W；`capacity=100` 时两者未提供。
4. 对阻抗 `capacity=315/500/630` 分别匹配 `≤4/≤5.5/≤6`，含正确比较符。
5. 模板从31字段变化为32字段，所有 Sheet 自动变为32行参数，不改生成器代码。
